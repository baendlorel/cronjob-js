✅ F28 pause() 之后，进程会在下一个分钟边界自行退出（code 0）

🟡 F29 系统时钟往回拨时，同一分钟会再跑一次 —— 不修，与 vixie cron 行为一致
   实测对照 Debian cron 3.0pl1 源码（/usr/sbin/cron）：cron_sync 只做一次对齐，
   之后 TargetTime 每轮固定 += 60，cron_tick 用 TargetTime 而不是 wall clock 判断，
   所以回拨后同一分钟不会重跑（代价是拨快时可能连续跳过几分钟）。
   本项目的循环本来就是"先排下一轮再跑"，回拨后下一次 tick 用的是当前时钟，
   确实会再命中一次；但这只在 NTP 把偏快的钟拨回来时发生，且与 F39 的夏令时重复一致。
   结论：接受为已知行为，不改代码。

🟡✅ F30 dir 里有 FIFO 或卡住的挂载时，runner 会静默停摆
   readFile 打开 FIFO 会一直阻塞，占住 libuv 线程池（默认 4 个）；连续 4 轮后连无关的 fs.readFile 也挂起。
   修复：loadFiles 先 stat，非普通文件（FIFO / 设备 / 目录）跳过并记 WARN，不做 readFile。
   实测：4 个 FIFO + real.js，单轮 17ms 结束，4 条 WARN，real.js 照常命中，无关 readFile 正常。
   nolater（utils.ts）没采用：race 只让 await 提前返回，底层线程仍在 FIFO 上阻塞，
   实测 8 个 FIFO 全部 race 超时后线程池依旧被占满。
   遗留：挂起的网络盘（stat 也会卡）没有解法，触发时线程池同样会被耗光。

🟡✅ F31 每轮都把整个文件读进内存，实际只需要文件头

   实测 214MB 的 .js：单轮 346ms / RSS +321MB → 8ms / RSS +1MB，content 恰好 65536 字节，表达式仍能识别。

🟡✅ F39 有夏令时的时区：回拨那天同一钟点跑两次，前跳那天该钟点被跳过
   实测：America/New_York 2026-11-01 01:30 出现两次，30 1 * * * 两个 UTC 时刻都命中；
   2026-03-08 的 30 2 * * * 全天 0 次命中。默认的 Asia/Shanghai 没有夏令时，不受影响。
   crontab（Debian cron 8 的 man page，即 vixie cron 系）的行为：
     "If the time has moved forwards, those jobs which would have run in the time that was skipped
      will be run soon after the change. Conversely, if the time has moved backwards by less than
      3 hours, those jobs that fall into the repeated time will not be re-run."
     "Only jobs that run at a particular time (not @hourly, nor with '*' in the hour or minute
      specifier) are affected. Jobs which are specified with wildcards are run based on the new
      time immediately."
     "Clock changes of more than 3 hours are considered to be corrections to the clock."
   即：前跳被跳过的那次会补跑、回拨的重复不重跑；只影响固定时刻，通配符按新时间走；±3h 才算 DST。
   本项目的 tick 只看 wall clock，回拨会重复、前跳会跳过，与 cron 正好相反。
   处理（不改 tick 语义）：新增行内标记 `@cronutc <5 段>`，只让这一条按 UTC 解析；
   UTC 无夏令时，对 DST 敏感的定时写它即可规避。`@cron` 的行为保持原样，README 已写明。
   实现：CronGroupItem 增加 timezone 字段，parseExp 增加可选 timezone 参数，
   getJobs/--list 用每条表达式自己的 timezone 判断和展示（--list 行首标 UTC）。
   实测：`@cron 0 9 * * *` 与 `@cronutc 0 9 * * *` 混排时各自按自己的时区命中；
   上海 09:00 只命中前者，UTC 09:00 只命中后者。

🟠✅ F44 umask 为 002 的机器上，runner 启动即失败（F40 的回归）
   ensureDir 按当前 umask 建目录，checkDirPermissions 紧接着拒绝 group 可写的目录。
   Debian/Ubuntu 开了 USERGROUPS_ENAB 时，普通用户登录 shell 的 umask 就是 002；
   pm2 daemon 会把启动它时的 umask 传给应用（实测在 umask 002 下启动 pm2，应用 umask=2）。
   结果是 dir 被建成 775 后立刻被自己拒绝，这类机器上第一次部署就起不来；umask 022 下正常。
   修复：ensureDir 统一 mkdirSync(dir, { recursive: true, mode: 0o755 })；0755 不带 group/other 写位，
   任何 umask 下只会更收紧，检查与建目录不再互相打架。
   实测：umask 002 + 尚不存在的 dir → 不再报错，dir/logDir mode 均为 755。
   回归用例 tests/initialize.test.ts「creates new dirs with 0755 even under umask 002 (F44)」
   （进程内 set umask 002，结束后恢复）。

🟠✅ F45 说明文字里提到 @cronutc 时，调度和 --list 用的时区不一致
   extractCron 优先认 @cron，按 cx.timezone 解析；getJobItem 却只要整行包含 @cronutc
   就把 timezone 标成 'UTC'。这个标签会被 --list 拿去重新 parse，所以展示和实际调度对不上。
   实测（timezone=Asia/Shanghai）："// @cron 0 9 * * * 也可以写成 @cronutc"
     调度：上海 09:00 命中、UTC 09:00 不命中；--list：显示 "UTC 0 9 * * *"，下次运行 17:00。
   修复：时区只由 extractCron 决定一次，它返回 { cron, timezone }，getJobItem 删掉第二次 UTC_REGEX 搜索，
   直接 list.push({ ...extracted, group })；时区只有一个来源，调度与 --list 必然一致。
   实测：'@cron' 与 '@cronutc 0 9 * * *' 混排时各自按自己的时区命中，--list 显示 UTC 与调度一致。

🟡✅ F46 同一行既有 @cron 又有 @cronutc 时，这一行被静默丢弃（随 F45 一并修复）

🟡✅ F47 --list 显示的解释器是 none，与实际运行不符（F43 的回归）
   --list 分支在 loadRuntime() 之前就 exit，getDefaultInterpreter 读到的是 fallback 映射，
   fallback 里只有 .js/.mjs/.cjs，于是 a.ts → "none"、b.sh → "none"。
   用户会以为 .ts/.sh 不被支持。上一轮回复里说"不影响输出正确性"是错的。
   修复（两道）：
   (a) cronjob() 把 loadRuntime() 提到 --list 分支之前，--list 也拿到真实命令；
   (b) 删掉 fallback：getDefaultInterpreter 只从 loadRuntime() 填好的映射里取，
       不再有那份只含 .js/.mjs/.cjs 的残缺表。调用方本来就是 cronjob()，
       它的一定会先探测，所以不需要兜底（测试里手动调 loadRuntime() 走同一流程）。
   实测：a.ts → "tsx a.ts"、c.js → "<node> c.js"、b.sh/d.sh → "bash a.sh"，没有 none。
   回归用例 tests/list.test.ts「解释器列是探测后的真实命令，不是 none（F47）」。

🟡✅ F50 权限检查只看 dir / logDir 本身，不看父目录和子目录 —— 不修，只写进文档
   F40 的威胁模型是"能写 dir 就等于能以 runner 身份执行代码"，这个检查有两个缺口：
   (a) 父目录：dir=…/shared/jobs，shared 是 777、jobs 是 755 → 检查通过、正常启动。
       其他用户可以把 jobs 改名移走，再放一个自己建的 jobs 目录。
   (b) 子目录：dir 是 755，dir/team/ 是 777 → 检查通过，team/x.js 照常被 glob 和执行。
   两者都需要错误配置的共享目录才会触发，属于检查的完整性问题，不是新漏洞。
   修法候选：(a) 沿 realpath 向上逐层检查到 /（sticky bit 的 /tmp 除外）；
           (b) loadFiles 里 stat 已经拿到 mode/uid，顺手拒绝属主不对或 other 可写的脚本。
   结论：不做。逐层向上检查会引入一长串平台差异（sticky bit、符号链接、Windows），
   与"极简、不为错误配置兜底"的定位不符。
   已处理（仅文档）：README 的 Permissions 一节写明"只检查 dir / logDir 本身，
   不向上看父目录、也不重新检查子目录"，并给出两种绕过场景，把责任交给部署方。
