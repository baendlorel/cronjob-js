F1. 定时器把"调度时刻"当成"本轮时间"，任务必然晚一分钟，且会重复跑
────────────────────────────────────────
位置：
  src/cron/task.ts:5-16
  src/index.ts:33（now 直接传给 shouldRun）

原因：
  runTask() 在"排下一轮定时器"时取 const now = new Date()，
  但真正到点回调时，传给 fn 的仍是上一轮排定时器时抓的那个 now。
  setTimeout 回调里没有重新取时间。

实测（node src/cron/task.ts 直接跑，3 分钟）：
  tick wall=00:25:00.046  now=00:24:48.953  stale=11.09s
  tick wall=00:25:58.329  now=00:25:00.061  stale=58.27s
  tick wall=00:26:00.015  now=00:25:58.333  stale=1.68s
  tick wall=00:26:58.334  now=00:26:00.015  stale=58.32s
  tick wall=00:27:00.047  now=00:26:58.337  stale=1.71s

后果：
  a) "00:25:00" 这一分钟的任务，实际在 00:25:58 甚至 00:26:00 才判定；
     也就是说所有任务至少晚约 1 分钟。
  b) 同一分钟会被判定两次（见上面 00:25 出现两次），任务重复执行。
     实测：// @cron 15 * * * * 的任务在 08:15:58 和 08:16:00 各跑了一次。
  c) 依赖事件循环唤醒时机（WSL/负载高时定时器会早/晚一两秒），
     行为不可复现。

修法：
  setTimeout 回调内部取 new Date() 作为本轮 now，不要复用排定时器时的 now。
  下一轮的分钟边界也要用回调内的当前时间重新算（递归调用已经每次都重算了，
  唯独 fn(now) 用的是旧值）。
ℹ️已改为new Date()

✅ 已修复并验证（2026-11-21，commit 3eee1ef + 补充修复）
  3eee1ef 把回调里的 fn(now) 改成 fn(new Date())，主症状（晚一分钟、同一分钟判定两次）已消失。
  但复核时发现原修法不完整：定时器会早于分钟边界触发（实测 WSL 下 -360~-460ms），
  此时 new Date() 仍属上一分钟，下一轮又会把边界算到同一分钟，导致同一分钟连跑两次。
  实测（只加 new Date()、不加边界判断）：
    09:06:00 / 09:06:58 / 09:07:00  → 09:07 这一分钟仍然跑了两遍
  已补 [src/cron/task.ts:10-19]：回调触发时若 Date.now() < 边界，则重新排到边界再跑。
  补丁后实测 3 分钟：
    09:18:00.017 Start / 09:19:00.005 / 09:20:00.018，每分钟恰好一次，任务日志同频。

  src/run.ts:22            path.relative(config.dir, filepath)

  日志路径 logs/sub/a.js.log 也正确（path.relative 拿到绝对路径后结果正确）。

  [src/syntax/extract.ts:119] 直接用这个结果替换默认解释器。

  实测：
    #!/usr/bin/env node      → spawn envnode.js 成功，日志 "envnode ran"
    #!/bin/bash -e           → args 正确切分，脚本正常执行

    #!/bin/bash              → 正常

  不用特判。真正的坑是原来把整行 "usr/bin/env node" 当成一个文件名。

F4. 用 PATH 检测 tsx，却用模块解析加载 tsx；.ts 任务全部失败且没有告警
────────────────────────────────────────
位置：
  src/interpreter.ts:22-26   detectCommand('tsx') → node --import tsx
  src/initialize.ts:15-19    orTsx() 的告警分支（而且 initialize 根本没被调用，见 F8）

实测（.ts 任务，系统 PATH 上有 tsx）：
  [Spawned] path=t.ts pid=...
  [Exit] path=t.ts pid=... code=1
  日志内容：Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'tsx' imported from /tmp/cjshe/proj/jobs/

原因：
  spawnSync('tsx') 只能证明 PATH 上有可执行文件（全局装的 tsx 就是这种），
  但子进程里 'tsx' 是作为模块从 cwd 往上找 node_modules 的。
  全局安装的 tsx 不可被 import，于是 --import tsx 必然失败。
  同时 hasTsx 为 true，所以连 [Warn] 都不会打。

后果：
  "tsx 缺失只警告，.ts 回退 node" 这条约定在两种情况下都不成立：
  - PATH 有、模块找不到：静默失败；
  - PATH 没有：args=[] 纯 node 跑 .ts，语法不兼容时同样静默失败。

修法：
  二选一，并让告警真实生效：
  a) 直接 spawn tsx 可执行文件：cmd='tsx', args=[filepath]；
  b) 用 createRequire(import.meta.url).resolve('tsx') 拿到绝对路径，
     再传 --import <绝对路径>。
  检测阶段应当真的执行一次（例如 spawnSync(cmd, ['--import', 'tsx', '-e', ''])），
  通过才算可用。

ℹ️帮我改成cmd='tsx'这种的。

✅ 已修复并验证（工作区未提交）
  [src/interpreter.ts] .ts 现在 cmd = detectCommand('tsx') ?? process.execPath，args = []；
  hasTsx 改为 tsx !== null。不再用 --import tsx，检测和启动走同一条 PATH，不存在分裂。

  实测：
  - 有 tsx（PATH 上）：cmd='tsx'，.ts 任务确实被 tsx 拉起；
  - 无 tsx（PATH 去掉 tsx）：回退 node 直接跑，Node 22 / 26 下装类型注释的 .ts 都能跑通；
  - tsx 存在但自身坏了（本机全局 tsx 装了 win32 的 esbuild，
    在 WSL 下直接跑 `tsx types.ts` 也报同样错误）——这属于环境问题，
  不是 runner 的问题，换一台正常的机器即可。

  遗留（不在 F4 范围，见 F8/F9 仍未修）：
  hasTsx 的告警在 initialize() 里，而 initialize() 仍未被调用，
  所以"tsx 缺失"这条提示目前还是不会打印。

F6. @cronend 之后 group 不归零，块后的独立 @cron 行被并入块
────────────────────────────────────────
位置：
  src/syntax/extract.ts:90-111   group 只在 BEGIN 时 ++，END 时只改 inCronBlock

实测：
  输入：
    // @cronbegin
    // @cron 0 9 * * *
    // @cronend
    // @cron 0 9 * * *      ← 块外，应为 group 0
    // @cron 0 9 * * *      ← 块外，应为 group 0
  输出：
    list = [ {exp:" 0 9 * * *", group:1},
             {exp:" 0 9 * * *", group:1},
             {exp:" 0 9 * * *", group:1} ]

后果：
  块后面的所有独立 @cron 行都挂在最后一个块的分组上，按 group 去重后只算 1 次。
  修好 F5 之后这条会让"本该跑 3 次"变成"只跑 1 次"，属于同一类漏跑。

修法：
  END 时把 group 复位为 0；块的编号用单独的计数器，不与"块外"共用同一个变量。

✅ 已由你手动修复（commit 84b703a），复核通过
  实际改法比建议更简：BEGIN 时 group 计数，入 list 时写 `group: inCronBlock ? group : 0`
  （src/syntax/extract.ts:110），块外天然是 0，不需要 END 复位。
  块编号只增不减也没问题——每个块一个唯一编号，跨块不会误合并。

  复核结果（cron 都写 0 9 * * *，now = 09:00，count 即应 spawn 次数）：
    块 + 块外 2 行      list=[块:1, 块外:0, 块外:0]          count=3  ✅
    两个块斜接          list=[块A:1, 块B:2]                    count=2  ✅
    块内 2 行都命中     list=[1,1]                             count=1  ✅（按组去重，符合约定）
    块外 3 行           list=[0,0,0]                           count=3  ✅
    嵌套 / 未闭合 / 孤立 @cronend   均为 null + Error 日志       ✅

F7.ℹ️ @cron 后面的说明文字会让整条配置被静默丢弃
——无所谓
────────────────────────────────────────

已随「改用 cron-parser」一并处理（工作区未提交）
  [src/syntax/extract.ts] extractCron 现在按空白切 token：
  - token < 5            → 不调度（见下方 F12 的说明，cron-parser 会自动补齐段数）
  - 前 6 段合法          → 报 "Seconds-level cron is not supported" 并跳过该行
  - 其余                 → 取前 5 段校验，之后视为说明文字
  实测：
    @cron 0 9 * * *                → "0 9 * * *"
    @cron 0 9 * * * 每天九点        → "0 9 * * *"
    @cron 0 9 * * * 每天 9 点       → "0 9 * * *"
    @cron 0 9 * * * 2026           → "0 9 * * *"（2026 不是合法秒位，按说明处理）
    @cron 0 9 * * * 5              → 报秒级错误并跳过
    @cron 0 9 * *                  → null（段数不足）
    @cron 0 0 9 * * *              → 报秒级错误并跳过
  已知取舍：5 段后面跟纯数字说明（如 "… 5"）会被判成秒级并跳过，
  同理 5 段后跟第二个合法 cron（重复写了一遍）也会被判成秒级。
  这是「先取 6 位校验」这条规则的固有歧义，按约定可接受。
